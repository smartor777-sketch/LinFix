# Guard: защита от шторма соединений

Guard — «предохранитель» LinFix. Он следит за логом TgWsProxy и останавливает
прокси, если CF-путь Telegram перестал работать, а клиент продолжает в цикле
переподключаться.

## Зачем это нужно

Если CF-домены отваливаются, происходит лавина:

```
CF-путь недоступен
  → Telegram-клиент переподключается в цикле
  → TgWsProxy открывает всё новые исходящие соединения
  → канал и NFQUEUE забиваются
  → zapret начинает тормозить весь трафик, а не только Telegram
```

Guard обрывает эту цепочку: прокси останавливается, сеть остаётся живой.
Остановка — не «поломка», а осознанная защита; после починки CF-пути прокси
запускается заново.

## Как работает

Раз в минуту (`linfix-guard.timer`) Guard:

1. читает **только новые строки** `~/.config/TgWsProxy/proxy.log`
   (по offset и inode, а не файл целиком);
2. считает строки `CF proxy failed` за окно;
3. если число ошибок ≥ порога, проверяет **TLS-доступность CF-доменов**
   (3 домена из state, иначе встроенный fallback-список);
4. останавливает TgWsProxy **только если ошибки И TLS-тест провален**.

Одного всплеска ошибок недостаточно: если TLS проходит, Guard пишет `WARN`
и ничего не трогает.

## Автоотключение H2 (c 0.5.11)

С версии 0.5.11 у Guard есть второй предохранитель — для сломанного
H2-пути к Cloudflare. Бывает так, что TCP/TLS/H2 до CF открывается, но CF
не отдаёт заголовки ответа: медиа в Telegram перестаёт грузиться, а в логе
появляется:

```
H2 DETAIL CLOSE lane=1 [channel=18 ... phase=headers ... down=0 ...]
```

Guard считает такие зависания (а без `verbose` — серию `H2 ... request
failed: ReadTimeout/WriteError/...`). Если за окно набралось **5** событий,
он:

1. делает бэкап `config.json` TgWsProxy;
2. выставляет `"h2": false`;
3. перезапускает `tgwsproxy`, чтобы медиа пошло через WS-CF;
4. пишет событие `status=fallback`, `h2_disabled=true` в
   `~/.local/state/linfix/guard-state.json`.

Прокси при этом **не останавливается**: WS-CF путь рабочий. В «Диагностике»
появляется предупреждение с подсказкой вернуть H2, когда CF снова начнёт
отдавать заголовки:

```bash
linfix tgws config --h2 on && linfix tgws restart
```

Порог `5` выбран так, чтобы не реагировать на единичные таймауты: слабый
канал и мобильная сеть дают их и в норме.

## Значения по умолчанию

| Параметр | Значение | Где задаётся |
|---|---|---|
| `enabled` | `true` | `[guard]` в `/etc/linfix/config.toml` |
| `error_threshold` | 20 ошибок | там же |
| `window_seconds` | 60 с | там же |
| Период проверки | 60 с | `data/systemd/user/linfix-guard.timer` |
| Доменов для TLS-теста | 3 | `guard.check_guard()` |

## Как включить и выключить

```bash
linfix guard status      # текущее состояние и последнее срабатывание
linfix guard check       # прогнать проверку сейчас (--no-stop — без остановки)
linfix guard on          # включить (через helper, root)
linfix guard off         # выключить
```

В панели — **Настройки → Guard**. Значение пишется в `/etc/linfix/config.toml`
через `linfix-helper config.guard`, то есть с бэкапом и правами root.

Важно: одного флага в конфиге мало — проверки запускает пользовательский
таймер `linfix-guard.timer`. `linfix guard on|off` (и «Сохранить» в панели)
включает или выключает и флаг, и таймер:

```bash
systemctl --user status linfix-guard.timer     # должен быть active (waiting)
systemctl --user list-timers linfix-guard.timer
```

Если таймер не запущен, Guard не делает ничего, даже когда `enabled = true`.

## Что нужно один раз после установки

Пакет кладёт юниты в `/usr/lib/systemd/user`, но пользовательские юниты
включаются от имени пользователя. LinFix делает это сам при
`linfix guard on` / «Сохранить» в панели. Проверить вручную:

```bash
systemctl --user daemon-reload
systemctl --user enable --now linfix-guard.timer
```

Без этого строки `Guard PASS` в «Диагностике» будут говорить, что защита
включена, а таймер при этом не тикает.

## Где смотреть результат

- **Статус** и **Диагностика** в панели: `Guard PASS: включён, срабатываний
  не было (порог 20/60 с)` либо `FAIL` с причиной.
- `linfix doctor` — строка `Guard`.
- Файл события: `~/.local/state/linfix/guard-state.json` (права `0600`):
  `status`, `detail`, `failures`, `threshold`, `tls_ok`, `stopped`,
  `last_trip`.
- Курсор чтения лога — `~/.local/state/linfix/guard.json`; удаление файла
  заставляет Guard перечитать лог с начала.

## Что делать, если Guard сработал

Guard сам пишет подсказку в событие. Порядок действий:

```bash
linfix domains test --all     # какие CF-домены живы
linfix domains update         # обновить список и hostlist
linfix domains test --all     # убедиться, что TLS проходит
linfix tgws start             # поднять прокси обратно
```

Если CF-путь всё ещё недоступен, лучше оставить прокси остановленным: так
сеть и zapret продолжат работать нормально.

## Когда Guard стоит выключить

- вы вручную и часто гоняете `domains test/update`, и остановка мешает
  диагностике;
- вы отлаживаете сам CF-путь и хотите видеть полный лог без вмешательства;
- на машине, где TgWsProxy останавливать нельзя ни при каких условиях
  (например, единственный канал связи).

## Ограничения

- Guard не «лечит» CF-путь, а только предотвращает шторм. Домены всё равно
  надо обновлять (`linfix domains update`).
- Guard читает только формат лога TgWsProxy с `CF proxy failed`; при смене
  формата логов регулярное выражение нужно обновить
  (`src/linfix/guard.py`, `CF_FAILURE_RE`).
- Без найденного `proxy.log` Guard возвращает `WARN` и ничего не делает —
  это ожидаемое поведение для tray-режима, пока прокси ни разу не стартовал.
- В CLI-режиме (headless) Guard работает так же: тот же таймер, тот же лог.
