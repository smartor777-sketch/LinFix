# Решения по реализации

Дата: 20.11.2026. Основано на SPEC 19 («если ответов нет — использовать дефолты»)
и фактах из [INVESTIGATION.md](INVESTIGATION.md).

## D1. Поддерживаем zapret2 и классический zapret

На целевой машине установлен **zapret2** (`/opt/zapret2`, `nfqws2`,
`zapret2.service`), а не раскладка `bol-van/zapret` из SPEC 8.1.
`zapret.detect_zapret()` проверяет оба варианта: `zapret2.service` и
`zapret.service`, бинарники `nfqws2`/`nfqws`. Имена путей и юнита не
хардкодятся — они берутся из процесса и systemctl.

## D2. Целевой hostlist

Пишем в первый `--hostlist` без `.gz`, предпочитая файл с `user` в имени.
На этой машине это `/opt/zapret2/ipset/zapret-hosts-user.txt`.
Сжатый `zapret-hosts.txt.gz` — база установщика, её не трогаем.
Если в конфиге задан `[zapret] hostlist`, он имеет приоритет.

## D3. Сохраняем стиль переводов строк

Реальный user-hostlist имеет **CRLF**. Merge определяет доминирующий стиль и
дописывает строки тем же стилем, чтобы не переписывать 29 756 строк и не
создавать гигантский diff. SPEC 8.3 разрешает CRLF.

## D4. Идемпотентность merge без « churn» даты

Если все домены уже есть, файл не меняется и бэкап не создаётся — даже если
изменилась дата. Маркер `# netfix: tgws cf domains (updated YYYY-MM-DD)`
добавляется только при первом добавлении. Новые домены вставляются после
последнего маркера, старые домены никогда не удаляются (SPEC 10.6).

## D5. Тесты на stdlib unittest

На машине нет `pip`, `ensurepip` и `pytest` (Python 3.12.3 из Mint).
Тесты написаны через `unittest`, поэтому запускаются без зависимостей и
одновременно собираются pytest'ом, если он появится:

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -t . -v
```

## D6. Конфиг и дефолты

`/etc/netfix/config.toml`; при отсутствии файла используются дефолты SPEC 7
(это не ошибка). Переопределение пути — `--config` или `NETFIX_CONFIG`.
Секретов в системном конфиге нет.

## D7. Границы helper

`netfix-helper` принимает только `domains.merge` и `zapret.restart`.
Пути обязаны быть абсолютными, канонизируются через `Path.resolve()` и должны
лежать под `/opt/netfix`, `/opt/zapret`, `/opt/zapret2`, `/opt/tgwsproxy`,
`/etc/netfix`, `/var/lib/netfix`. Запись в `*.gz` запрещена. Никакого
`shell=True`.

## D8. VPN/TUN — WARN, а не FAIL

На момент первого замера был активен `vpn0` (split-default `0.0.0.0/1` +
`128.0.0.0/1`); позже VPN отключился сам. TLS-тест CF-доменов проходит в обоих
случаях, даже без добавления их в hostlist — значит, в текущей сети эти домены
сейчас не блокируются. Поэтому:

- doctor показывает WARN при наличии VPN-маршрутов **или** интерфейса
  `tun*`/`vpn*`/`wg*` (состояние динамическое);
- успешный TLS-тест не считается доказательством работы zapret;
- для честной проверки нужна сеть, где SNI реально режется, либо сравнение
  «с zapret / без zapret».

## D9. Ответы на открытые вопросы SPEC 19

1. Версия Mint: **22.3 (Zena)**, Python 3.12.3.
2. Zapret уже установлен (**zapret2**); автоустановка — M2, не MVP.

## D10. Ограничение текущего окружения агента

Агент работает от uid 1000 в песочнице с `no_new_privs`: `sudo` и запись в
`/opt` невозможны. Поэтому M0–M1 выполняют только чтение и безопасные прогоны
(`--dry-run`, фейковый helper), а baseline-снимок лежит в `backups/`. Все
реальные правки zapret должны выполняться пользователем через
`sudo`/`pkexec` и `netfix-helper`.

## D11. State — источник правды по доменам

`/var/lib/netfix/state.json` хранит не только дату и sha256, но и сам список
CF-доменов. Это позволяет:

- повторно применить домены после обновления/переустановки zapret;
- работать `domains update --offline`, если GitHub недоступен;
- проверять hostlist в doctor без сетевого запроса.

Digest считается по нормализованному множеству (сортировка, нижний регистр),
поэтому перестановка строк в источнике не вызывает ложного «обновления».

## D12. Транзакция domains.apply и откат

Привилегированная операция — одна транзакция helper:
merge → state → restart → verify. Если после рестарта служба не active или
процесс `nfqws`/`nfqws2` не найден:

1. hostlist восстанавливается из бэкапа;
2. выполняется повторный рестарт;
3. ошибка и журнал пишутся в state (`last_error`);
4. CLI возвращает код 5.

Повторный `domains update` увидит `last_error` и попробует снова, даже если
формально «добавлять нечего».

## D13. Эскалация прав

- CLI никогда не пишет в `/opt` и не вызывает systemctl для системных служб
  напрямую (кроме user-службы TgWsProxy).
- Для `domains update` вызывается `netfix-helper`:
  root — напрямую; иначе `pkexec`, затем `sudo`.
- `NETFIX_HELPER` — явное переопределение команды helper для dev/тестов;
  в этом режиме эскалация не выполняется.
- Если helper не установлен, CLI честно просит запустить команду через sudo.
