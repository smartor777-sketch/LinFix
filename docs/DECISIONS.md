# Решения по реализации

Дата: 20.11.2026. Основано на SPEC 19 («если ответов нет — использовать дефолты»)
и фактах из [INVESTIGATION.md](INVESTIGATION.md).

## D18. Название: LinFix vs LinFix

- Репозиторий/проект переименован в **LinFix** (пакет `linfix`, команда `linfix`),
  чтобы не путать с существующим продуктом **LinFix**.
- SPEC.md — документ с ТЗ и планом реализации; в нём название **LinFix**
  (основное название продукта). Для Linux-реализации имя репозитория/пакета —
  LinFix. SPEC не переписываем.
- Пути/идентификаторы обновлены: `/var/lib/linfix/state.json`, `/etc/linfix/config.toml`,
  `/etc/linfix/profiles.toml`, `/usr/libexec/linfix-helper`, `linfix-guard.*`.
- Ярлышки сервисов — имитация стиля Zapret2, см. [docs/DESKTOP-ICONS.md](docs/DESKTOP-ICONS.md).

## D1. Поддерживаем zapret2 и классический zapret

На целевой машине установлен **zapret2** (`/opt/zapret2`, `nfqws2`,
`zapret2.service`), а не раскладка `bol-van/zapret` из SPEC 8.1.
`zapret.detect_zapret()` проверяет оба варианта: `zapret2.service` и
`zapret.service`, бинарники `nfqws2`/`nfqws`. Имена путей и юнита не
хардкодятся — они берутся из процесса и systemctl.

## D2. Целевой hostlist

Пишем в первый `--hostlist` без `.gz`, предпочитая файл с `user` в имени.
На этой машине это `/opt/zapret2/ipset/zapret-hosts-user.txt`.
Сжатый `zapret-hosts.txt.gz` — база установщика, её не трогаем.
Если в конфиге задан `[zapret] hostlist`, он имеет приоритет.

## D3. Сохраняем стиль переводов строк

Реальный user-hostlist имеет **CRLF**. Merge определяет доминирующий стиль и
дописывает строки тем же стилем, чтобы не переписывать 29 756 строк и не
создавать гигантский diff. SPEC 8.3 разрешает CRLF.

## D4. Идемпотентность merge без « churn» даты

Если все домены уже есть, файл не меняется и бэкап не создаётся — даже если
изменилась дата. Маркер `# linfix: tgws cf domains (updated YYYY-MM-DD)`
добавляется только при первом добавлении. Новые домены вставляются после
последнего маркера, старые домены никогда не удаляются (SPEC 10.6).

## D5. Тесты на stdlib unittest

На машине нет `pip`, `ensurepip` и `pytest` (Python 3.12.3 из Mint).
Тесты написаны через `unittest`, поэтому запускаются без зависимостей и
одновременно собираются pytest'ом, если он появится:

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -t . -v
```

## D6. Конфиг и дефолты

`/etc/linfix/config.toml`; при отсутствии файла используются дефолты SPEC 7
(это не ошибка). Переопределение пути — `--config` или `LINFIX_CONFIG`.
Секретов в системном конфиге нет.

## D7. Границы helper

`linfix-helper` принимает только `domains.merge` и `zapret.restart`.
Пути обязаны быть абсолютными, канонизируются через `Path.resolve()` и должны
лежать под `/opt/linfix`, `/opt/zapret`, `/opt/zapret2`, `/opt/tgwsproxy`,
`/etc/linfix`, `/var/lib/linfix`. Запись в `*.gz` запрещена. Никакого
`shell=True`.

## D8. VPN/TUN — WARN, а не FAIL

На момент первого замера был активен `vpn0` (split-default `0.0.0.0/1` +
`128.0.0.0/1`); позже VPN отключился сам. TLS-тест CF-доменов проходит в обоих
случаях, даже без добавления их в hostlist — значит, в текущей сети эти домены
сейчас не блокируются. Поэтому:

- doctor показывает WARN при наличии VPN-маршрутов **или** интерфейса
  `tun*`/`vpn*`/`wg*` (состояние динамическое);
- успешный TLS-тест не считается доказательством работы zapret;
- для честной проверки нужна сеть, где SNI реально режется, либо сравнение
  «с zapret / без zapret».

## D9. Ответы на открытые вопросы SPEC 19

2. Zapret уже установлен (**zapret2**); автоустановка — M2, не MVP.

## D10. Ограничение текущего окружения агента

Агент работает от uid 1000 в песочнице с `no_new_privs`: `sudo` и запись в
`/opt` невозможны. Поэтому M0–M1 выполняют только чтение и безопасные прогоны
(`--dry-run`, фейковый helper), а baseline-снимок лежит в `backups/`. Все
реальные правки zapret должны выполняться пользователем через
`sudo`/`pkexec` и `linfix-helper`.

## D11. State — источник правды по доменам

`/var/lib/linfix/state.json` хранит не только дату и sha256, но и сам список
CF-доменов. Это позволяет:

- повторно применить домены после обновления/переустановки zapret;
- работать `domains update --offline`, если GitHub недоступен;
- проверять hostlist в doctor без сетевого запроса.

Digest считается по нормализованному множеству (сортировка, нижний регистр),
поэтому перестановка строк в источнике не вызывает ложного «обновления».

## D12. Транзакция domains.apply и откат

Привилегированная операция — одна транзакция helper:
merge → state → restart → verify. Если после рестарта служба не active или
процесс `nfqws`/`nfqws2` не найден:

1. hostlist восстанавливается из бэкапа;
2. выполняется повторный рестарт;
3. ошибка и журнал пишутся в state (`last_error`);
4. CLI возвращает код 5.

Повторный `domains update` увидит `last_error` и попробует снова, даже если
формально «добавлять нечего».

## D13. Эскалация прав

- CLI никогда не пишет в `/opt` и не вызывает systemctl для системных служб
  напрямую (кроме user-службы TgWsProxy).
- Для `domains update` вызывается `linfix-helper`:
  root — напрямую; иначе `pkexec`, затем `sudo`.
- `LINFIX_HELPER` — явное переопределение команды helper для dev/тестов;
  в этом режиме эскалация не выполняется.
- Если helper не установлен, CLI честно просит запустить команду через sudo.

## D14. Установка TgWsProxy

- Бинарник скачивает и устанавливает helper (`tgws.install`): CLI не пишет в
  `/opt`. Скачивание — только HTTPS, SHA256 из `asset.digest`, лимит 200 МБ,
  атомарная замена, режим 0755.
- `.deb`/`.rpm` не используются (SPEC 9.1).
- Конфиг и user-unit пишутся от пользователя. Конфиг создаётся только если его
  нет; существующий не перезаписывается.
- В MVP `host` разрешён только loopback: `127.0.0.1`, `localhost`, `::1`.
- Путь конфига — предположение (`~/.config/TgWsProxy/config.json`). После
  первой живой установки его нужно подтвердить и при необходимости поправить
  `CONFIG_CANDIDATES` (см. M2-REPORT).

## D15. Guard: окно, offset и условие остановки

- Один запуск guard = одно окно (таймер раз в 60 с). Читаются только новые
  строки лога по offset; offset и inode хранятся в
  `~/.local/state/linfix/guard.json`, при truncate/ротации чтение с нуля.
- Прокси останавливается только при `failures >= error_threshold` **и**
  провале TLS-теста всех выбранных CF-доменов. Если TLS проходит — только WARN:
  единичные сбои не должны рвать рабочий прокси.
- Факт срабатывания и причина пишутся в
  `~/.local/state/linfix/guard-state.json`; doctor показывает последнее
  срабатывание.
- `linfix guard on|off` меняет только `[guard] enabled` в системном конфиге
  через helper (бэкап + валидация TOML), не переписывая остальные ключи.

## D16. update/setup без неожиданных изменений

- `setup` и `update` по умолчанию только показывают план.
- Реальные действия выполняются с `--yes`; `--dry-run` гарантированно ничего
  не меняет.
- `update --check` только сравнивает версии/даты.
- `setup` не устанавливает zapret автоматически: если его нет — печатает
  инструкцию и возвращает код 3.

## D17. Профили сетей

- `linfix profile set <uuid> --name X` тоже пишет файл на root (`/etc/linfix/profiles.toml`);
  через helper `profile.set` с бэкапом, валидацией TOML и атомарной записью 0644.
- `linfix profile clear` работает по `nmcli --active` (первый активный UUID); если
  `nmcli` нет или нет активных соединений — печатается понятное сообщение.
- В MVP (`M4`) смена стратегии запрещена: `STRATEGIES = {"general"}`. Структура
  `[profiles."<uuid>"]` готова для продвинутых `strategy = "cf" | "direct" | "auto"`.
- Dispatcher `90-linfix` вызывает helper `profile.apply <uuid>` — агент там не
  выполняется (минимальное окружение), всё решается через helper.


## D18. Guard: автоотключение H2 и WS-CF fallback (0.5.11)

- H2-путь к Cloudflare может открываться, но не отдавать заголовки ответа:
  `phase=headers`, `down=0`, канал закрывается по таймауту. Медиа в Telegram
  при этом не грузится, хотя текстовые сообщения идут.
- Guard считает такие зависания (`H2_STALL_RE`) и, без `verbose`, серию
  `H2 ... request failed: ReadTimeout/WriteError/...`. Порог — **5 событий
  за окно**: единичные таймауты на слабом канале не должны менять конфиг.
- При срабатывании Guard делает бэкап `config.json`, выставляет
  `"h2": false`, перезапускает `tgwsproxy` и пишет событие
  `status=fallback`, `h2_disabled=true`.
- Прокси при этом **не останавливается**: WS-CF путь рабочий, и медиа идёт
  через него. Это отличается от старого `tripped`, где служба глушилась.
- В doctor строка Guard показывает причину и подсказку вернуть H2:
  `linfix tgws config --h2 on && linfix tgws restart`.
- `linfix guard check` считает `fallback` успешным статусом (exit 0).
- H2 не включается обратно автоматически: решение должно быть осознанным,
  после проверки, что CF снова отдаёт заголовки.

## D19. CF-профиль zapret и worker-домен (0.5.12)

- Причина «текст есть, медиа нет» — профиль `tcpseg:pos=0,1`: он режет
  TCP-сегменты и ломает H2-тела больше ~16–24 КБ. Канал отправляет запрос,
  не получает заголовки и закрывается по таймауту.
- Рабочий профиль для CF-доменов: `fake:blob=fake_default_tls:tcp_md5`
  + `multidisorder:pos=1,midsld`. Проверено: H2 принимает 256 КБ за 0.4 с.
- Профиль ограничен отдельным hostlist (`linfix-cf-hosts.txt`), остальные
  правила zapret не меняются. Воспроизводимо: `scripts/apply-cf-profile.sh`.
- Публичный список с GitHub содержит `.com`-домены в NXDOMAIN; рабочий
  список — 20 `.co.uk`-доменов из `cf-domains.txt`.
- `linfix tgws config --worker-domain <домен>` пишет `cfproxy_worker_domain`
  и включает `cfproxy_worker_enabled`. Ключ `cfproxy_worker_enabled`
  добавлен в `ALLOWED_CONFIG_KEYS`; `cfproxy_user_domain_enabled`
  по-прежнему защищён от изменения через LinFix.
- Код Worker'а лежит в `deploy/cf-worker/` (worker.js + wrangler.toml).

## D20. Guard не читает историю лога при первом запуске (0.5.13)

- При первом запуске Guard читал весь `proxy.log` с начала. Старые записи
  о зависаниях H2 (до починки профиля zapret) сразу же отключали рабочий H2.
  Это наблюдалось на практике: после `enable --now linfix-guard.timer` прокси
  переключился на WS-CF.
- Теперь при отсутствии курсора Guard ставит его в конец файла и разбирает
  только новые строки. История не влияет на решение.
- Поведение вынесено в параметр `skip_history` (по умолчанию `True`), тесты
  истории используют `skip_history=False`.
- Заодно поиск установленного helper вынесен в `util.installed_helper()`,
  чтобы тесты не зависели от того, установлен ли пакет на машине.

## D21. Проверка профиля CF и режим GitHub (0.5.14)

- Добавлена команда `linfix domains profile` и кнопка «Проверить профиль CF»
  в разделе «Домены»: TLS + HTTP/2 `POST /api` телом 256 КБ.
- Обычный TLS-тест этого не видит: `tcpseg` открывает домен, но ломает
  большие H2-тела. Новая проверка прямо показывает «TLS проходит, но
  H2-тело не передаётся — профиль ломает медиа».
- Глубокий `blockcheck2` («Подобрать стратегию») остаётся для случая, когда
  не открываются сами домены; для медиа он не нужен.
- Режим ротации GitHub не отключён, но предупреждение в GUI теперь честное:
  текущий список `.com`-доменов не резолвится, медиа и часть трафика
  перестанут работать. Рабочий режим — «пользовательские домены».

## D22. Guard проверяет H2 живым запросом (0.5.15)

- Наблюдалось ложное срабатывание: Guard увидел 8 записей о зависаниях H2
  (остатки прошлого профиля zapret) и отключил рабочий H2.
- Теперь перед отключением Guard делает живой запрос: TLS + HTTP/2 POST
  256 КБ (`cfprofile.check_profile`). Если тело проходит — остаётся `WARN`
  «в логе N зависаний, но живой запрос проходит — H2 не отключаю».
- Ложное отключение ломало медиа; проверка стоит несколько сотен
  миллисекунд раз в минуту, только при подозрении.
- Проверка вынесена в `h2_probe` (для тестов), чтобы тесты не ходили в сеть.

## D23. Раздельные списки доменов в GUI (0.5.16)

- Раньше раздел «Домены» показывал только список для hostlist zapret
  (загруженный с GitHub), а текущую ротацию TgWsProxy — лишь текстом.

  - «Тест TLS» и «Проверить профиль CF» доступны для обоих списков.

- В режиме GitHub правки пользовательского списка только сохраняются

- Найден и удалён дубликат `get_cf_domains` в конце `api.py`, который
  перекрывал новую версию.

## D24. Подробное предупреждение у переключателя ротации (0.5.18)

- Переключатель «Пользовательские домены ↔ GitHub» может сразу сломать
  доступ к Telegram, поэтому диалог подтверждения переписан.
- Для перехода на GitHub: тип `WARNING`, кнопка «Всё равно переключить»,
  по умолчанию выбрана «Отмена» (Enter не подтверждает опасное действие).
- В тексте: что произойдёт (смена источника, автообновление, рестарт
  службы и обрыв соединений), почему это опасно сейчас (`.com`-домены в
  NXDOMAIN, профиль zapret привязан к нашим `.co.uk`), и когда это
  допустимо — только если пользовательский набор полностью перестал
  работать (проверено «Тест TLS» и «Проверить профиль CF»).
- Для обратного перехода — обычный вопрос без «страшных» акцентов.

## D26. Окно ведёт себя как обычное приложение (0.5.19)

- Раньше в `window.py` стоял `set_keep_above(True)`, поэтому панель висела
  поверх всех окон, а при разворачивании из трея могла оказаться позади.
- Теперь `keep_above=False` и `Gdk.WindowTypeHint.NORMAL` — окно
  подчиняется оконному менеджеру как обычно.
- При показе из трея окно однократно поднимается (`present()` + фокус),
  но без постоянного «поверх всех».
- Минимизация по-прежнему уводит окно в трей, закрытие (X) — тоже.
- Тест проверяет `type_hint == NORMAL`, отсутствие `skip_taskbar` и
  `keep_above is False`.

## D27. Настраиваемые домены для подбора стратегий (0.5.20)

- Раньше `rutracker.org` и `telegram.org` были жёстко зашиты в `api.py`
  и `helper.py`.
- Теперь список задаётся секцией конфига:

  ```toml
  [blockcheck]
  domains = ["rutracker.org", "telegram.org", "flibusta.is"]
  ```

- В «Диагностике» появилось поле «Домены для подбора» с кнопкой

  (бэкап + валидация TOML).
- Диалог подбора показывает, какие домены будут проверяться.
- Пустой список в конфиге трактуется как значения по умолчанию, чтобы
  случайная правка не оставила подбор без целей.
- `flibusta.is` добавили в список, но по состоянию на 22.11.2026 её TLS
  не завершается (TCP открыт, хендшейк виснет) — при подборе она, скорее
  всего, даст только провалы. Домен легко убрать из поля.

## D28. «Диагностика Telegram» без дублирования «Сайтов» (0.5.21)

- В «Диагностике» кнопка называлась «Сетевая диагностика» и включала разбор
  SNI/DPI — то же, что умеет раздел «Сайты», но хуже: без действий и только
  для Telegram.
- Теперь кнопка называется «Диагностика Telegram» и проверяет только путь до
  Telegram: DC и порты 443/80/5222, пинги до опорных узлов, подмену DNS
  (система vs DoH), троттлинг и скорость медиа.
- Разбор SNI/DPI удалён из `netdiag.py` (`DpiResult`, `BLOCK_SNI`,

## D31. Честный выбор активного профиля и подсказки doctor (0.5.24)

- `zapret.active_profile_for` сравнивал домен с **именами файлов**
  hostlist (`host.endswith("linfix-cf-hosts.txt")`), поэтому CF-домены
  никогда не попадали в CF-профиль: функция возвращала глобальный `tcpseg`.
- Теперь профиль хранит полные пути (`hostlist_paths`), и покрытие
  проверяется по фактическому содержимому списка. Порядок сохранён:
  профиль с hostlist совпадает первым, «голый» — только если выше никто
  не совпал.
- Из-за этого `doctor` показывал ложный WARN про «голый» профиль. Теперь
  он проверяет, перекрывает ли тот CF-домены: если CF-профиль стоит раньше,
  статус PASS с пояснением.
- Подсказка Guard: если событие `status=warn` и живой запрос H2 прошёл,
  doctor показывает PASS «действий не требуется», а не совет перезапускать.
- Добавлены тесты `tests/test_zapret_profiles_order.py`: CF-домен → CF-профиль,
  прочие → глобальный, «голый» первым остаётся глобальным, отсутствие файла
  не ломает выбор.
