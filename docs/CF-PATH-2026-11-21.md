# Разбор CF-пути и Telegram — 21.11.2026

## Контекст

- Рабочая копия: LinFix **v0.5.10**, `main`/`private/main` = `898b839`.
- Публичный репозиторий: `44c0d45` (v0.5.10).
- Узел разработки (`Dev.play2go.cloud`): LinFix **0.5.0**.
- Симптом: периодические `TimeoutError`, `no fallback available`, затем жалоба
  «в Telegram нет новых сообщений».

## Исходное состояние

- `zapret2`: active; `tgwsproxy`: active, режим `cli`.
- В юните закреплены три домена:
  `pclead.co.uk`, `offshor.co.uk`, `cakeisalie.co.uk`.
- Первый профиль в `/opt/zapret2/config` был с «голым» путём:

  ```text
  --filter-tcp=443 --filter-l7=tls /opt/zapret2/ipset/zapret-hosts-rut.txt \
    --payload=tls_client_hello \
    --lua-desync=tcpseg:pos=0,1:ip_id=rnd:repeats=1 --new
  ```

  Так как путь указан без `--hostlist=`, профиль совпадал с любым TLS-доменом,
  включая CF. Следующий профиль с `multisplit` для hostlist zapret поэтому
  никогда не срабатывал.

## Проверенный вариант 2 и откат

Был сделан бэкап `/opt/zapret2/config.bak-linfix-20261121-2137`, после чего
первый профиль ограничен через
`--hostlist=/opt/zapret2/ipset/zapret-hosts-rut.txt`, а `zapret2` перезапущен.

Результат — **отрицательный**:

- пачки `gaierror(-2)` прекратились;
- но TLS-хендшейк ко всем трём CF-доменам перестал проходить:
  `openssl s_client` давал таймаут;
- `h2_tcp` вырос с 8 до 144, `h2_err` — с 4 до 48;
- за 10 минут: 2460 `TimeoutError`, 817 `no fallback available`,
  38 `ConnectTimeout`;
- `down` рос примерно на 20 КБ/мин вместо обычных сотен КБ/мин.

Предположение: `multisplit:pos=1:seqovl=568:seqovl_pattern=t4pda` не
десинхронизирует TLS ClientHello CF-доменов, потому что паттерн `t4pda` в нём
отсутствует. Глобальный `tcpseg`, наоборот, обеспечивал рабочий хендшейк.

Конфиг был **полностью откачен из бэкапа**, `zapret2` перезапущен. После отката:

- TLS по всем трём доменам: `Verify return code: 0 (ok)`;
- HTTPS `/` отвечает `404` (ожидаемо, корень не WS-endpoint);
- разбор LinFix показывает для всех трёх доменов профиль
  `tcpseg:pos=0,1:ip_id=rnd:repeats=1`.

## Перезапуск TgWsProxy

Перезапускался дважды, **без изменения конфига**:

- режим остался `cli`;
- юнит с теми же тремя `--cfproxy-domain`;
- секрет, порт и список доменов не менялись.

После отката и перезапуска сброшены залипшие H2-lane. Свежая статистика
23:23: `total=702 active=9 ws=0 h2=535 h2_tcp=4 h2_err=3`,
`up=622.7KB down=7.0MB` — трафик стабильно идёт.

`ws=0` при этом **норма**: такой же показатель был в рабочей Windows-конфигурации
NetFix, где медиа тоже шли через H2/CF. Резервного WS-пула в этой схеме нет.

## Проверка узла разработки

- `zapret2`: active.
- `tgwsproxy`: inactive, но enabled; последний лог от 20.11 с нулевым трафиком.
- Конфиг старого образца: `cfproxy_user_domain: []`, `linfix_mode: tray`.
- Наши три `.co.uk`-домена с dev доступны: DNS → `188.114.96.3` /

- Но GitHub-автосписок с `.com`-доменами (`virkgj.com`, `vmmzovy.com`,
  `mkuosckvso.com`, …) на dev **не резолвится**.
- Все 20 `.co.uk`-доменов из `cf-domains.txt` резолвятся нормально.

Вывод: сетевая доступность CF есть, но старая версия 0.5.0 с пустым
`cfproxy_user_domain` не может использовать авто-пул. Переход на GitHub-авторежим
сейчас дал бы нерабочий путь.

## Сравнение с Windows NetFix

Источник: `docs/TELEGRAM-CONNECTION-PARAMS.md` (приватный репозиторий).

- TgWsProxy на Windows — та же версия **1.11.4**, что и на Linux.
- Одинаковые `dc_ip` (`2/4 → 149.154.167.220`), `h2=true`, `pool_size=4`.
- Windows использует авто-пул GitHub (`cfproxy_user_domain: []`) и `ws=0`,
  при этом `down=91.7MB` — значит H2/CF-путь там здоров.
- В Windows-конфиге есть `ws_keepalive_interval=30`, но в Linux-исходниках
  1.11.4 этого поля нет: вероятно, патч Windows-сборки NetFix.
- `forceNetworkOk=true` влияет только на индикацию в UI.
- Секреты различаются — это ожидаемо для разных установок.
- В Windows-пуле присутствует `sorokdva.co.uk`, который мы ранее проверили
  и решили не возвращать из-за ретрансмиссий.

Вывод: разница в поведении объясняется не версией TgWsProxy, а сетью,
набором доменов и DNS. Копировать Windows-конфиг на Linux нельзя.

## Итоговые решения

1. Оставить глобальный `tcpseg` в `/opt/zapret2/config` без `--hostlist=`.
2. Оставить три закреплённых CF-домена; не включать GitHub-авторежим.
3. Не возвращать `sorokdva.co.uk`.
4. Код LinFix **не менялся**: `git status` чистый, HEAD `898b839`.
5. Бэкап `/opt/zapret2/config.bak-linfix-20261121-2137` сохранён.
