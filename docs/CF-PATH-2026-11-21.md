# Разбор CF-пути и Telegram — 21.11.2026

## Контекст

- Состояние на момент разбора: LinFix **v0.5.10**.
- Узел разработки (имя скрыто): LinFix **0.5.0**.
- Симптом: периодические `TimeoutError`, `no fallback available`, затем жалоба
  «в Telegram нет новых сообщений».

## Исходное состояние

- `zapret2`: active; `tgwsproxy`: active, режим `cli`.
- В юните закреплены три домена:
  `pclead.co.uk`, `offshor.co.uk`, `cakeisalie.co.uk`.
- Первый профиль в `/opt/zapret2/config` был с «голым» путём:

  ```text
  --filter-tcp=443 --filter-l7=tls /opt/zapret2/ipset/zapret-hosts-rut.txt \
    --payload=tls_client_hello \
    --lua-desync=tcpseg:pos=0,1:ip_id=rnd:repeats=1 --new
  ```

  Так как путь указан без `--hostlist=`, профиль совпадал с любым TLS-доменом,
  включая CF. Следующий профиль с `multisplit` для hostlist zapret поэтому
  никогда не срабатывал.

## Проверенный вариант 2 и откат

Был сделан бэкап `/opt/zapret2/config.bak-linfix-20261121-2137`, после чего
первый профиль ограничен через
`--hostlist=/opt/zapret2/ipset/zapret-hosts-rut.txt`, а `zapret2` перезапущен.

Результат — **отрицательный**:

- пачки `gaierror(-2)` прекратились;
- но TLS-хендшейк ко всем трём CF-доменам перестал проходить:
  `openssl s_client` давал таймаут;
- `h2_tcp` вырос с 8 до 144, `h2_err` — с 4 до 48;
- за 10 минут: 2460 `TimeoutError`, 817 `no fallback available`,
  38 `ConnectTimeout`;
- `down` рос примерно на 20 КБ/мин вместо обычных сотен КБ/мин.

Предположение: `multisplit:pos=1:seqovl=568:seqovl_pattern=t4pda` не
десинхронизирует TLS ClientHello CF-доменов, потому что паттерн `t4pda` в нём
отсутствует. Глобальный `tcpseg`, наоборот, обеспечивал рабочий хендшейк.

Конфиг был **полностью откачен из бэкапа**, `zapret2` перезапущен. После отката:

- TLS по всем трём доменам: `Verify return code: 0 (ok)`;
- HTTPS `/` отвечает `404` (ожидаемо, корень не WS-endpoint);
- разбор LinFix показывает для всех трёх доменов профиль
  `tcpseg:pos=0,1:ip_id=rnd:repeats=1`.

## Перезапуск TgWsProxy

Перезапускался дважды, **без изменения конфига**:

- режим остался `cli`;
- юнит с теми же тремя `--cfproxy-domain`;
- секрет, порт и список доменов не менялись.

После отката и перезапуска сброшены залипшие H2-lane. Свежая статистика
23:23: `total=702 active=9 ws=0 h2=535 h2_tcp=4 h2_err=3`,
`up=622.7KB down=7.0MB` — трафик стабильно идёт.

`ws=0` при этом **норма**: такой же показатель был в рабочей Windows-конфигурации
NetFix, где медиа тоже шли через H2/CF. Резервного WS-пула в этой схеме нет.

## Проверка узла разработки

- `zapret2`: active.
- `tgwsproxy`: inactive, но enabled; последний лог от 20.11 с нулевым трафиком.
- Конфиг старого образца: `cfproxy_user_domain: []`, `linfix_mode: tray`.
- Наши три `.co.uk`-домена с узла разработки доступны: DNS → адреса

Вывод: сетевая доступность CF есть, но старая версия 0.5.0 с пустым
`cfproxy_user_domain` не может использовать авто-пул. Переход на GitHub-авторежим
сейчас дал бы нерабочий путь.

## Сравнение с Windows NetFix

Источник: `docs/TELEGRAM-CONNECTION-PARAMS.md` (приватный репозиторий).

- TgWsProxy на Windows — та же версия **1.11.4**, что и на Linux.
- Одинаковые переопределения `dc_ip` (DC2/DC4 → один IP Telegram),
  `h2=true`, `pool_size=4`.
- Windows использует авто-пул GitHub (`cfproxy_user_domain: []`) и `ws=0`,
  при этом `down=91.7MB` — значит H2/CF-путь там здоров.
- В Windows-конфиге есть `ws_keepalive_interval=30`, но в Linux-исходниках
  1.11.4 этого поля нет: вероятно, патч Windows-сборки NetFix.
- `forceNetworkOk=true` влияет только на индикацию в UI.
- Секреты различаются — это ожидаемо для разных установок.
- В Windows-пуле присутствует `sorokdva.co.uk`, который мы ранее проверили
  и решили не возвращать из-за ретрансмиссий.

Вывод: разница в поведении объясняется не версией TgWsProxy, а сетью,
набором доменов и DNS. Копировать Windows-конфиг на Linux нельзя.

## Медиа в Telegram: отключение H2 (22.11.2026)

### Симптом

- Текстовые сообщения и обновления приходят.
- В **любом** канале не загружаются посты с медиа: фото, видео, файлы.
- Ошибок в логе Telegram почти нет, только `PEER_ID_INVALID` по отдельным
  каналам — то есть клиент считает, что сеть есть.

### Что показал debug-лог TgWsProxy

С включённым `verbose=true` и `h2=true`:

```text
H2 DETAIL lane=2 [channel=19 ... phase=headers age_ms=3020
  send_ms=0 wait_headers_ms=3019 up=252 down=0 ...]
H2 channel=19 closed lane=2 ... duration=8.0s
  pending=1 receiving=0 ready_bytes=0 down=0 waiting_headers=1
```

То есть H2-канал до CF открывался, запрос уходил (44–252 байта),
но Cloudflare **не возвращал заголовки ответа**. Через 8 секунд канал
закрывался по таймауту, и медиа не начинало качаться.

При этом тот же CF по WebSocket работал:

```text
WS CONNECT DC2 media route=cf setup_ms=238
```

### Почему WS-пул всегда пуст

`ws=0`, `pool=0/...` — это не поломка пула, а следствие блокировки:

```text
WS pool connect kws2.web.telegram.org/apiws via <IP DC Telegram>
  (fronting=True): TimeoutError()
WS pool refilled DC2m: 0 ready
```

Пул подключается не к имени домена, а к IP Telegram DC, а этот IP в
текущей сети недоступен:

```text
TCP <IP DC>:443 -> FAIL
TCP <IP DC>:443 -> FAIL
```

Поэтому патч шаблона `ws_domains()` (`kws{dc}-1...` → `kws{dc}...`) ничего бы
не дал: меняется только SNI, TCP всё равно идёт на закрытый IP.

### Решение

В `~/.config/TgWsProxy/config.json` выставлено:

```json
"h2": false,
"verbose": false,
"cfproxy_user_domain_enabled": true,
"cfproxy_user_domain": ["pclead.co.uk", "offshor.co.uk", "cakeisalie.co.uk"]
```

После перезапуска `tgwsproxy` медиа пошло через WS-CF fallback:

- `down` вырос до **17.1 МБ** за время проверки;
- ошибок `WARNING/ERROR` в логе нет;
- медиа-сессии открываются стабильно, setup 190–700 мс;
- текст и медиа работают одновременно.

### Бэкапы конфига

- `~/.config/TgWsProxy/config.json.bak-linfix-20261122-015339` — перед `h2=false`.
- `~/.config/TgWsProxy/config.json.bak-linfix-20261122-020003` — перед `verbose=false`.

### Вывод

- H2-путь к CF в текущей сети сломан на уровне получения заголовков ответа;
  WS-CF путь рабочий.
- Рабочая конфигурация: `h2=false`, три закреплённых домена, режим `tray`.
- Это изменение только конфигурации TgWsProxy; код LinFix не менялся.
- При обновлении TgWsProxy или изменении поведения CF стоит повторить
  проверку с `h2=true`.

## Ротация «пользовательские домены» / GitHub (22.11.2026)

Вопрос: актуален ли сейчас переключатель ротации TgWsProxy?

Ответ: **переключатель исправен, но режим GitHub в текущих условиях вреден.**

- В режиме «пользовательские домены» TgWsProxy берёт ровно наш список
  (20 `.co.uk`-доменов). Это рабочая конфигурация.
- В режиме «домены с GitHub» TgWsProxy очищает `cfproxy_user_domain` и
  тянет список из
  `raw.githubusercontent.com/Flowseal/tg-ws-proxy/.../cfproxy-domains.txt`.
- На 22.11.2026 этот список содержит 20 `.com`-доменов
  (`virkgj.com`, `vmmzovy.com`, …), у которых **нет A-записей** (NXDOMAIN).
  Переключение на GitHub оставит прокси без рабочих доменов.
- Ротация в `state.json` хранит 20 `.co.uk`-доменов и не обновляется с
  GitHub, поэтому режим «пользовательские домены» стабилен.

Вывод: оставить «пользовательские домены». Режим GitHub имеет смысл только
если upstream снова начнёт публиковать резолвящиеся домены — это надо
проверять перед переключением.
